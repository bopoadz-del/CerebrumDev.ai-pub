# Automotive Safety Intelligence Pilot — Design Specification

> **Status:** Draft — awaiting implementation planning.
> **Release goal:** One complete, deployable, browser-operable Automotive Safety Intelligence product generated by CerebrumDev.ai from The_Fork platform template + Cerebrum-Blocks automotive domain kit.

---

## 1. Objective

Prove that CerebrumDev.ai can generate a complete, secure, usable domain platform outside construction by building and deploying an **Automotive Safety Intelligence Pilot**.

The pilot must allow a user to:

1. Log in through a browser.
2. Open the Automotive Core Knowledge workspace and ask automotive safety questions.
3. Receive streamed answers with cited evidence from official public NHTSA data.
4. Create a private project, upload private automotive documents, and receive grounded answers.
5. See public-foundation and private-project evidence clearly separated.
6. Use admin controls to view foundation-pack status and activate validated pack versions.

This release replaces the planned sequence of separate production-embedding, vector-store, retrieval, activation and UI micro-phases with **three large, product-shaped PRs**.

## 3. Embedding model decision

### 3.1 What the code defaults say

The_Fork code still has a legacy fallback to `minishlab/potion-base-8M` (256-dim) when `RAG_EMBEDDING_MODEL` is unset. However, the repo also contains a newer, explicitly qualified `chunks_v2` ingestion path.

### 3.2 Live inspection evidence

Local data stores in `C:/Users/user/The_Fork/data/` were inspected on 2026-07-11:

| Artifact | Finding |
|---|---|
| `the_fork.db` table `chunks_v2` | 21,672 rows |
| `the_fork_cleaned.db` table `chunks_v2` | 10,931 rows |
| Stored `embedding_model` in `chunks_v2` | `BAAI/bge-small-en-v1.5` exclusively |
| Stored `embedding_dim` in `chunks_v2` | `384` exclusively |
| `RAG_VECTOR_NAMESPACE` default in code | `v2` (`app/core/rag/vector_store.py:140`) |
| `rag_render_bulk_ingest_checkpoint.json` | model `BAAI/bge-small-en-v1.5`, dim `384`, namespace `v2`, 6,770 chunks written for `dg2_infra_pack_1` |
| `bulk_render_ingest.log` | model `BAAI/bge-small-en-v1.5`, dim `384`, `chunks_v2: 7538` |
| `EMBEDDER_DECISION.md` | Approved: `BAAI/bge-small-en-v1.5` as Phase-1 rebuild embedder |

### 3.3 Decision

The automotive pilot uses:

```text
embedding_model: BAAI/bge-small-en-v1.5
embedding_dim: 384
vector_namespace: v2
distance_metric: cosine
normalization: l2
chunk_table: chunks_v2
```

The legacy `chunks` table and 256-dim potion path remain available in The_Fork but are **not** used for the pilot. The generated platform must set `RAG_EMBEDDING_MODEL=BAAI/bge-small-en-v1.5` and `RAG_VECTOR_NAMESPACE=v2` explicitly and must write identity columns (`embedding_model`, `embedding_dim`, `embedding_normalized`) on every chunk to guard against cross-model contamination.

## 4. Release structure: three large PRs

### PR 1 — Domain Platform Generation

**Goal:** A reproducible CerebrumDev.ai generator that emits a domain-neutral, automotive-branded platform package from the pinned Fork template + hardened automotive kit.

**Scope:**

1. Fork-derived domain-neutral platform template in CerebrumDev.ai.
2. Automotive platform manifest (`automotive-safety-intelligence`).
3. Automotive Cerebrum-Blocks kit hardening:
   - `block_registry/automotive_v2/block.json` capability manifest.
   - Automotive expert prompt and default chat prompt.
   - Automotive knowledge base scaffold.
   - Bundled CLI artifacts in the kit manifest.
   - Source-pack and RAG-pack manifest enrichment.
4. Generator integration in `platform_packager.py`:
   - Consumes the automotive platform manifest.
   - Vendors the pinned Cerebrum-Blocks engine.
   - Copies automotive kit artifacts.
   - Emits docker-compose + Render blueprint.
5. Reusable multi-user Google Drive connector core:
   - `DriveConnection`, `DriveFolderBinding`, `DriveSyncJob`, `DriveFileRecord`, `IndexedDocument`, `AuditEvent` data models.
   - CerebrumDev.ai factory OAuth flow, folder picker and folder binding.
   - Generated-platform Drive module, OAuth routes and migrations.
   - Manifest feature flag (`features.google_drive`).
   - Separate OAuth app configuration for factory vs. generated deployments.
   - Encrypted refresh-token storage and ownership isolation tests.
6. Reproducible generation test.

**Gate:** `python -m pytest backend/tests/test_platform_packager.py backend/tests/test_automotive_domain_smoke.py -q` passes; generated package builds with `docker-compose build`.

### PR 2 — Automotive Intelligence

**Goal:** A working automotive foundation corpus with real semantic embeddings, pgvector/BM25 indexing, public/private retrieval separation, activation, citations and a 50-question evaluation.

**Scope:**

1. NHTSA data harvester (official public APIs / bulk downloads only):
   - recalls (2015–present)
   - defect investigations (2015–present)
   - consumer complaints (2022–present)
   - safety ratings (2015–present)
   - manufacturer communications where safely available
   - vPIC make/model/manufacturer metadata for normalization
2. Canonical automotive record models (`recall`, `complaint`, `investigation`, `safety_rating`, `manufacturer_communication`, `vehicle_identity`).
3. Normalization and deterministic chunking reusing CerebrumDev.ai Phases 4–5, extended to the real embedding/indexing path rather than duplicated.
4. Production semantic embedding with `BAAI/bge-small-en-v1.5` (384-dim).
5. Postgres/pgvector HNSW cosine index + BM25 `tsvector` index in the `chunks_v2` namespace.
6. Hybrid retrieval (semantic + lexical, RRF fusion) with automotive identifier boosts.
7. Layer-aware retrieval:
   - `automotive_core_v1`: platform-owned, read-only public foundation.
   - `client_private`: project-scoped private documents, including Google Drive-imported files.
8. Google Drive client-private routing:
   - Drive-imported documents index only into `client_private`.
   - Citation metadata labels Drive evidence as `knowledge_layer: client_private` and `source: google_drive`.
   - Public `automotive_core_v1` remains unchanged by Drive imports.
9. Activation and citation contract:
   - Every result carries `knowledge_layer`, `collection_id`, source authority, score.
   - Citations distinguish confirmed evidence from inference.
9. 50-question automotive golden evaluation (exact recall, ODI/investigation lookups, make/model/year, complaint patterns, safety ratings, cross-source, no-answer).

**Gate:** evaluation meets:

```text
exact campaign-number retrieval: 100%
exact ODI/investigation identifier retrieval: 100%
top-5 evidence recall across answerable questions: >= 85%
answers with required citations: 100%
unsupported evidence presented as fact: 0
private corpus leakage: 0
cross-user project leakage: 0
foundation/client layer mislabelling: 0
```

### PR 3 — Pilot Release

**Goal:** A deployed, browser-operable automotive pilot instance with converted frontend, admin controls, security/E2E tests and final release report.

**Scope:**

1. Frontend conversion from The_Fork base:
   - branding, navigation, empty states, project terminology, quick actions.
   - source labels: "Automotive Core" / "Private Project".
   - quick actions: Check recalls by vehicle, Search campaign number, Review complaint patterns, Compare safety records, Summarize investigation.
2. Admin foundation-pack panel:
   - pack version, status, harvest timestamp, source families, counts, embedding identity, index namespace, evaluation result, activation status.
   - build/resume, verify, evaluate, activate, rollback with confirmation guard.
3. Client-private document overlay:
   - project-scoped upload, indexing, deletion, non-contamination of `automotive_core_v1`.
   - Google Drive connect, folder bind, sync and private-indexing browser flow.
4. Google Drive isolation verification:
   - User A connects Drive, binds folder, asks question, receives private Drive citation + Automotive Core context.
   - User B cannot see User A's Drive evidence.
   - Separate users can connect separate Drive accounts.
   - Disconnecting one account does not affect another.
   - File changes and deletions update only the correct private project index.
   - `automotive_core_v1` remains unchanged.
5. Generated deployment:
   - isolated database, storage, secrets, vector namespace.
   - Render blueprint and docker-compose stack.
5. Browser acceptance tests and security tests.
6. Live smoke test and final release report.

**Gate:**

## 5. Architecture

### 5.1 High-level flow

```text
User ──► Automotive Pilot (React + FastAPI)
            │
            ├──► Public foundation corpus: automotive_core_v1 (read-only, platform-owned)
            │       └── NHTSA recalls / complaints / investigations / ratings
            │           └── BAAI/bge-small-en-v1.5 embeddings ──► pgvector/BM25
            │
            └──► Private project corpus: client_private (project-scoped, owner-only)
                    └── uploaded service documents / manufacturer communications
                        └── same embedder, separate namespace/collection
```

### 5.2 Two-layer RAG

| Layer | Collection | Ownership | Visibility | Source class |
|---|---|---|---|---|
| Foundation | `automotive_core_v1` | Platform | Shared read-only | Approved official public data |
| Client overlay | `client_private` | User/Org/Project | Owner-authorized only | Private uploaded or connected documents |

Retrieval may combine both layers but every result must include:

```text
knowledge_layer
collection_id
project_id or foundation_pack_id
source title
source authority
source URL or document identity
record/reference identifier
retrieval score
```

Client-specific questions prefer relevant client evidence. The public foundation may supplement but must not override a directly relevant client record without explaining the difference.

### 5.3 Generated platform package

```text
{deploy}/
├── engine/                 # pinned Cerebrum-Blocks snapshot
├── app/containers/automotive.py
├── app/blocks/automotive_v2.py
├── app/core/automotive_*.py
├── app/prompts/automotive_expert.txt
├── app/knowledge/automotive_kb.json
├── default_chain.json
├── data/docs/              # small fixtures only; no full NHTSA corpus
├── Dockerfile
├── docker-compose.yml
├── render.yaml
├── entrypoint.sh
├── alembic/versions/       # platform migrations
├── frontend/               # React/Vite, automotive-branded
├── cli/
├── .env.example
└── build_metadata.json
```

The actual NHTSA records, chunks and embeddings are **not** committed to Git. They are produced as versioned build artifacts / object storage and loaded into the generated pilot's isolated Postgres/pgvector database.

### 5.4 Multi-user Google Drive integration

A reusable, domain-neutral Google Drive connector core serves two distinct integrations with strict isolation between them.

#### A. CerebrumDev.ai factory integration

Multi-user factory users can:

- Sign in to CerebrumDev.ai.
- Connect their own Google Drive account using OAuth.
- Select a folder through a Google folder picker.
- Bind the selected folder to a factory workspace.
- Import requirements, branding, configuration, approved source material or explicitly authorised customer documents.
- View sync and indexing progress.
- Resync, disconnect and delete imported/indexed data.

Ownership scope:

```text
organisation_id
user_id
factory_workspace_id
drive_connection_id
folder_binding_id
```

No user or organisation may see another organisation's Drive account, token, folder list, files or indexed content.

#### B. Generated client-platform integration

Every generated platform inherits multi-user Google Drive capability. Users can:

- Sign in to the generated platform.
- Connect their own Google Drive account.
- Select a folder.
- Bind it to a private project or workspace.
- Automatically sync and index supported documents.
- Ask questions using those documents.
- See citations labelled as private Google Drive evidence.
- Resync, disconnect and remove indexed content.

Ownership scope:

```text
tenant_id
user_id
project_id
drive_connection_id
folder_binding_id
```

Drive documents must index only into the client-private project RAG layer. They must never enter `automotive_core_v1` or any shared prebuilt domain RAG.

#### Isolation between products

CerebrumDev.ai and each generated deployment must use separate:

```text
Google OAuth applications
client IDs and secrets
redirect URIs
encryption keys
databases
token stores
audit records
sync jobs
private indexes
```

A Drive connection made in CerebrumDev.ai must not automatically exist in the generated automotive platform.

#### Multi-user connector entities

Minimum entities:

```text
Organisation or Tenant
User
Membership
DriveConnection
DriveFolderBinding
DriveSyncJob
DriveFileRecord
IndexedDocument
AuditEvent
```

Support personal bindings and role-controlled organisation-shared bindings.

#### Security requirements

- Read-only least-privilege Drive scope by default.
- Per-user OAuth.
- OAuth state validation and PKCE where supported.
- Encrypted refresh tokens at rest.
- No tokens in logs, API responses or generated packages.
- Folder-level binding; do not silently crawl the entire Drive.
- Cross-user and cross-tenant access prevention.
- Deleted or changed Drive files reflected in the private index.
- Disconnect and revocation workflow.
- Explicit indexed-data deletion policy.
- Audit trail for connection, binding, sync, failure, disconnect and deletion.

#### Generated-platform manifest feature flag

```json
{
  "features": {
    "google_drive": {
      "enabled": true,
      "multi_user": true,
      "personal_connections": true,
      "organisation_shared_bindings": true,
      "default_scope": "read_only"
    }
  }
}
```

## 6. Data ownership and storage

### What Cerebrum-Blocks Git owns

- `automotive_v2` block capability and registry manifest
- Domain prompts and system prompts
- Source-policy and RAG-pack manifests
- Normalization schemas and canonical record models
- Harvest definitions (URLs, endpoints, field mappings, refresh policy)
- Evaluation question definitions
- Small test fixtures (≤ few MB)

### What Cerebrum-Blocks Git does NOT own

- Full harvested NHTSA records
- Generated chunks
- Embedding vectors
- pgvector indexes
- Bulk downloaded binaries

### Where the corpus lives

1. **Build artifacts:** versioned downloadable archive or object-store tarball produced by the pack builder (e.g., Render disk, S3-compatible bucket, or CI artifact). The exact backend is chosen during implementation; the requirement is that it is outside Git and versioned.
2. **Runtime database:** the generated pilot's isolated Postgres/pgvector instance.

This prevents repository bloat and keeps pack updates reviewable.

- Private service histories

- User uploads (these belong in the client overlay)

## 8. Retrieval ranking

### 8.1 Identifier-aware lookup

Exact automotive identifiers receive deterministic lookup treatment:

```text
NHTSA campaign numbers
ODI complaint numbers
Investigation numbers
model year + make + model
vehicle component names
```

### 8.2 Layer-aware ranking

For questions clearly referring to a client vehicle, fleet, dealer or uploaded record:

```text
relevant client evidence
→ relevant automotive foundation evidence
→ unrelated evidence excluded
```

For general automotive safety questions:

```text
automotive foundation evidence
→ optional relevant client evidence only when explicitly applicable
```

### 8.3 Construction-specific boosts removed

Do not retain construction identifier boosts such as `VO`, `RFI`, `NCR`, `PRC`, `FIDIC clause`, `drawing reference`. Replace with manifest-driven automotive identifier boosts.

## 9. Automotive grounded assistant

The assistant must:

- Answer from retrieved evidence.
- Cite recall, complaint or investigation references.
- Separate confirmed evidence from inference.
- State the corpus harvest date when freshness matters.
- Avoid claiming a recall exists without supporting evidence.
- Avoid diagnosing mechanical failures as certain from complaint patterns.
- Distinguish complaints from official defect findings.
- Distinguish manufacturer communications from formal recalls.
- Say when evidence is insufficient.

Wired blocks: `automotive_v2`, `formula_executor_v2`, hybrid document retrieval, citation rendering.

No fine-tuning or LoRA in this release.

## 15. Risks

- Corpus freshness and refresh requirements.
- Official-data field inconsistencies across NHTSA APIs.
- Complaint narratives are reports, not confirmed defect findings.
- Source volume and indexing cost.
- Domain-template extraction may reveal hidden construction coupling.
- Embedding-model migration compatibility (mitigated by using the qualified `chunks_v2` / BGE-small 384 path).
- Deployment resource requirements.
- Private/public retrieval ranking calibration.
